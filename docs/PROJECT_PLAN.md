# 구축 계획

작성일: 2026-10-23

## 1. 프로젝트 목표

오픈소스 탄막 게임 Taisei Project를 실행하고, AI가 최고 난이도를 자동으로 클리어하도록 만든다.
이후 탄막의 색상·잔상·광원 등 시각 표현을 조정하여 탄막 패턴의 아름다움을 보여주는 영상을 제작한다.

- 최종 목표: 최고 난이도 전체 자동 클리어 및 재현 가능한 리플레이 확보.
- 현재 최우선 목표: Emscripten/WebAssembly 기반 웹 빌드와 브라우저 수동 플레이 완성. 이후 AI 작업을 시작한다.
- 기존 1~2주 자동 플레이 일정은 웹 전환 범위를 반영하여 재산정한다.
- 시각 표현 개선은 자동 플레이 기준선을 확보한 뒤 진행한다.
- 게임 버전, 빌드 명령, 연동 API는 소스 확인 후 확정한다.

## 3. 구현 방향

### 게임과 실행 환경

1. 실제 게임을 실행할 PC의 OS, GPU, 개발 도구를 확인한다.
2. Taisei 공식 저장소와 라이선스, 빌드 안내를 확인한다.
3. 검증한 커밋 또는 릴리스를 고정하고 원본 상태로 빌드한다.
4. 수동 플레이, 입력, 사운드, 프레임 속도, 리플레이 동작을 확인한다.
5. 동일 절차로 다시 실행할 수 있도록 설치·빌드·실행 명령을 문서화한다.

게임 실행은 우선 그래픽 환경이 있는 사용자 PC를 기준으로 한다. 서버·컨테이너의 빌드 성공과 실제 화면에서의 실행 성공을 각각 기록한다.

### 웹 전환 — AI보다 먼저

[웹 전환 계획](WEB_PORT_PLAN.md)과 [이슈 #2](https://github.com/kthss01/mini-danmaku-ai-claude/issues/2)를 따른다.
고정 소스의 Emscripten 설정을 우선 활용하되 웹 성공 여부는 실제 빌드·브라우저 플레이로 확인한다.
Windows 초기 실행은 완료되었지만 전체 수동 플레이는 미검증이다.

### 관측과 제어 — 웹 완료 이후

오픈소스의 장점을 살려 게임 내부 상태를 읽는 방식부터 검토한다.

- 관측 후보: 플레이어 위치·피격 판정·이동 속도, 탄 위치·속도·종류, 레이저, 적, 화면 경계, 잔기·봄, 스테이지·프레임.
- 제어 후보: 상하좌우, 저속 이동, 공격, 봄.
- 게임 루프와 관측·입력 적용 시점을 맞추고 고정 프레임 단위 실험을 지원한다.
- 한 패턴 반복 실행, 초기화, 시드 고정은 소스 지원 여부를 확인한 뒤 구현한다.
- Python 에이전트와 게임 사이의 통신 방식은 소스 구조와 성능을 확인한 뒤 결정한다.
- 화면 인식 방식은 후속 비교 대상으로 둔다.

프레임마다 Claude 또는 ChatGPT API를 호출하지 않는다. LLM은 개발·분석·실패 로그 해석을 돕고, 실시간 조작은 로컬 알고리즘이 수행한다. 모델 학습은 규칙 기반 기준선을 확보한 후 필요할 때 도입한다.

### 첫 자동 플레이 알고리즘

1. 공격 유지와 단순 이동으로 입력 연동을 검증한다.
2. 탄과 플레이어의 상대 위치·속도로 짧은 미래의 충돌 위험을 예측한다.
3. 이동 후보별 위험과 화면 경계를 평가하여 회피 방향을 선택한다.
4. 저속 이동과 봄 사용 조건을 추가한다.
5. 레이저·가속탄 등 예외 패턴을 실패 기록으로 보완한다.

내부 상태를 이용하는 에이전트임을 결과에 명시한다. 무적, 탄속 감소, 피격 판정 축소를 사용한 실험은 원래 규칙의 클리어 기록과 구분한다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |

| 2 | 웹 빌드·서빙 | 고정 도구로 새 checkout에서 재현 — 완료(2026-10-24) |
| 3 | 브라우저 수동 플레이 | 메뉴·탄막 구간·입력·오디오 검증 및 PR 머지 — 완료(2026-10-29. 오디오 청취 등 사람 확인은 사용자 결정으로 생략) |
| 4 | 웹 상태·입력 연동 | 별도 이슈에서 설계·검증 |

| 6 | 시각 표현·시연 | 동일 리플레이 비교 및 결과 정리 |

웹 경로의 실제 난이도 확인 전 AI 일정은 확정하지 않는다.

## 5. 탄막 표현 개선

- 후보: 색상 팔레트, 밝기·투명도, 잔상, 배경 대비, 블룸.
- 원본 표현과 개선 표현을 같은 리플레이로 비교한다.
- 원래 규칙 클리어용 프리셋은 탄 궤적·속도·개수·피격 판정을 유지한다.
- 패턴 자체를 바꾸는 연출 실험은 별도 프리셋과 별도 결과로 관리한다.
- GPU 부하, 평균 FPS, 프레임 지연을 확인한다.
- 영상과 스크린샷 공개 전 게임 코드·이미지·음원별 라이선스와 출처 표기를 확인한다.

## 6. 저장소 구조

```text
.
├── agent/       # 관측 모델, 위험 예측, 입력 정책
├── artifacts/   # 작은 결과 요약과 외부 산출물 안내
├── bridge/      # 게임과 에이전트 사이의 연동
├── configs/     # 실험 설정과 시각 표현 프리셋
├── docs/        # 환경 구축, 구조 분석, 실험 결과, 시각 표현 안내
├── scripts/     # 설치, 빌드, 실행, 평가 자동화
└── tests/       # 충돌 예측과 연동 등 핵심 동작 검증
```

초기에는 각 경로의 책임만 정의하고, 구현 언어와 연동 방식이 확정된 후 패키지 구조를 구체화한다. Taisei 원본 도입은 버전 고정과 수정 관리가 쉬운 방식을 선택하며, 서브모듈 또는 별도 포크 중 실제 빌드·배포 요구에 맞춰 확정한다. 대용량 영상, 빌드 산출물, 모델 파일은 일반 Git 커밋에서 제외한다.

## 7. 검증 기준

- 실행 환경, Taisei 커밋, 에이전트 커밋, 난이도, 캐릭터, 스테이지, 시드를 가능한 범위에서 기록한다.
- 생존 프레임, 피격 횟수, 봄 사용, 클리어 여부, FPS와 판단 시간을 기록한다.
- 특정 시드 1회 성공과 여러 시드 반복 성공을 구분한다.
- 연습 모드 성공과 전체 게임 성공을 구분한다.
- 최고 난이도 전체 클리어는 원래 게임 규칙에서의 실제 실행 결과와 리플레이로 확인한다.

## 8. AI 도구 활용

- Claude: 주요 구현과 코드 탐색에 활용하는 기본 도구.
- Codex: 환경 구축, 코드 수정, 검증, GitHub 문서·변경 관리에 활용.
- ChatGPT: 목표·우선순위 정리, 알고리즘 검토, 실험 결과 해석에 활용.

Claude를 주 구현 담당으로, Codex를 리뷰·검증 보조로 운영한다. 모든 다음 작업은 브랜치 → PR → 검증·리뷰 → 머지 순서로 완료한다. 동일 파일의 동시 수정을 피하고, 작업별 브랜치와 커밋으로 변경을 추적한다. 구현 과제에는 목표·수정 범위·완료 조건·실행 결과를 함께 남긴다.
